# MCP 自动解密与 Agent 续跑

## 1. 做了什么

把原来只负责 F8 的托盘程序扩展成了本机绿盾解密服务，并新增 `LdDecryptMcp.exe` 作为标准输入输出 MCP 适配器。Codex 或其他 Agent 现在可以先检查用户指定文件或文件夹的绿盾加密状态，必要时提交官方解密申请，等待加密头真正消失，然后自动回到原来的读取、分析或转换任务。本机还安装了配套 Codex 插件和 Skill，新任务可以直接发现四个解密工具。

同时补齐了文件夹递归检查、同用户命名管道权限、最多 10,000 个文件、跳过重解析点、设备路径拒绝、扫描不完整返回 `unverified`、普通明文绝不误提交、断线不带崩托盘、冷启动自动拉起托盘，以及 8 个并发 Agent 状态连接。MCP 同时兼容旧版 initialize 握手和 2026-07-28 的无状态 server/discover 协议。

## 2. 为什么做

过去 Agent 遇到绿盾密文时只能报错并让人手动选文件按 F8，解密后还得重新下达任务。真正想消除的是这次“人机接力”：既然电脑本身已经具备申请权限，Agent 就应当在用户授权范围内完成检查、申请、验证和续跑，同时仍保留绿盾官方审批链与审计记录。

## 3. 有什么值得记住的决策、坑或技术点

- 不抓取、不伪造也不重放远端通信，MCP 只复用已经验证的本机官方插件入口；快，但安全边界没有改变。
- “按钮点过了”不是成功信号。完成条件必须是已知绿盾 8 字节加密头消失并且文件可以读取，否则只能返回 `pending`、`unreadable` 或 `unverified`。
- 目录扫描遇到无权限子目录或重解析点时，绝不能因为已发现的几个文件解密完了就宣称整个目录成功，这类部分结果必须保守处理。
- MCP 冷启动托盘时，子进程不能继承适配器的标准输出句柄；否则工具结果已经返回，调用方仍会一直等不到进程管道关闭。
- 管道允许并发检查与等待，但真正发送申请仍用全局锁串行化，防止两个 Agent 把不同目标混进同一张申请单。
- Agent 行为约束和服务端校验缺一不可：Skill 规定只处理用户当前任务中的明确路径，服务端再限制绝对路径、设备路径和批量规模。

## 4. 一句话亮点

绿盾解密从“一键替人点”升级成“Agent 自己发现、自己申请、确认明文后继续干活”的闭环能力。
