# F8 绿盾本地直连申请

## 1. 做了什么

把 F8 从失败的“透明读取后生成明文副本”改成了真正的绿盾本地直连。程序现在直接调用安装目录里的 `LdMenuPlug.dll`，按照右键菜单原本的格式发送申请解密文件信号，等官方 `LdApproval` 的申请窗口出现后自动点击发送。确认直连稳定后，旧版菜单点击代码已从当前分支删除，只保留在 Git 历史中。

为了确认不是猜协议，先做了只初始化、不发命令的探针，确认当前策略中的第 10 类菜单正是启用状态的“申请解密”；随后只对刚才的测试副本发送本地信号，官方“新建申请”窗口成功弹出，并在测试阶段主动关闭窗口，没有提交申请。

## 2. 为什么做

透明复制在这台电脑上有一个根本问题：读取时能得到可读内容，但目标文件只要出现 `.docx`、`.xlsx`、`.pdf` 等受控扩展名，绿盾就会立即重新加密。普通流复制、Java 服务、临时后缀再改名，本质上都躲不过当前写入策略，所以继续修补复制方式价值不大。

真正耗时的部分其实是人为展开右键菜单和等待菜单状态。绿盾自己的 Shell 扩展最终也只是把选中文件交给本地菜单插件，因此直接调用这个本地入口更稳定，而且仍走官方申请、审批和审计链路。

## 3. 值得记住的决策、坑或技术点

普通“申请解密”在菜单插件里对应类型 10。菜单点击会为每个文件发送两份命令：命令 1 携带系统代码页路径，命令 `0x12` 携带 UTF-16LE 路径；结构中数据区为 512 字节，偏移 `0x204` 的整数表示是否为多选批次最后一个文件。新版严格复现这两份信号，并拒绝超长路径，避免静默截断。

插件初始化后可以常驻进程。新版启动时预热一次，本次运行期间后续 F8 不再重复加载和释放插件。官方窗口出现后优先查找可用的“发送/提交”按钮，找不到才使用原来的固定位置点击，因此兼顾速度和当前绿盾自绘界面兼容性。

不要再用进程伪装、改扩展名或直接拼服务器数据包。前两种会持续和加密驱动对抗，后一种涉及有状态审批事务；本地菜单插件才是当前版本最小、最贴近官方行为的入口。

## 4. 一句话亮点

不再和绿盾右键菜单赛跑：F8 直接把选中文件送进官方申请程序，审批链路照常，等待时间砍掉一大截。
